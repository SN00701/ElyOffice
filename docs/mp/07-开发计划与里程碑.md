### 4.2 M0-B（LO+LOK 构建）的现场诊断与续跑指引

**已解决的两个坑**

1. **`core.autocrlf` 必须是 false**：否则工作区是 CRLF，`.sh` 的 shebang 失效
   （`set -euo pipefail: invalid option name`），LO 补丁无法应用。已全仓库归一化为 LF。
2. **partial clone 的按需取 blob 会卡死**：LO 用 `--filter=blob:none` 稀疏检出，
   而 Ely 的 53 个补丁要改 `sw/`、`sc/`、`sd/`、`svx/`、`vcl/` 等**稀疏集之外**的文件；
   `apply-lo-patches.sh` 每次 `git show` 触发一次网络取 blob，在慢代理下等于卡死。
   **已修**：`build-libreoffice-win.sh` 先用 `git sparse-checkout set --no-cone` 把补丁涉及的文件
   （99 个）纳入稀疏集，再 `git read-tree -mu HEAD` —— **一次请求取回全部**。

**当前状态（2026-10-20 22:5x）**：源码稀疏检出完成（477 文件 + 99 个补丁文件），
`apply-lo-patches.sh` 正在执行；`config_host.mk` 与 `Makefile` 尚未生成。
构建目录 `F:\mpely-lo`（无空格），日志 `F:\mpely-lo\build.log`。

**续跑方式**

```bash
# Cygwin bash（路径含空格，必须用脚本文件，不要用 -c 拼接）
F:\cygwin64\bin\bash.exe '/cygdrive/e/trae pg/office_modpack/mpelyoffice/scripts/build-lo-win-run.sh'
```

**下一个可能的坑（按可能性排序）**
1. `git read-tree -mu HEAD` 在 non-cone 模式下可能退化为取回整棵树（观察到 5.8GB 的 pack）——
   若卡住，改用 `git -C lo-src fetch --filter=blob:none` 后逐目录 `git checkout` 补丁文件所在目录。
2. `autogen.sh` 需要 **VS 自带的 CMake**（`VC.CMake.Project` 组件）与 Cygwin 的 `make`；
   `--with-visual-studio=2022` 与本机 VS 2026（18.6）可能不匹配，必要时改为 `2026`。
3. 构建目录与 Cygwin 目录须加入 **Defender 排除项**，否则并行 configure 删不掉 `conftest.dir`。
4. 构建完成后必须保留补丁 `0044-lok-win32-paints-then-copies.patch`（否则表格只画 1×1 像素）。

### 4.3 过程中的两条硬教训

1. **`core.autocrlf` 必须为 false**：克隆时 Git for Windows 的默认 `autocrlf=true` 让工作区成了 CRLF，
   `.sh` 的 shebang 失效（`set -euo pipefail: invalid option name`），LO 补丁无法应用。
   已用 `git rm --cached -r . && git reset --hard` 全仓库归一化为 LF（上游 `AGENTS.md` 亦有此要求）。
2. **`git reset --hard` 会连同未提交改动一起回退**：本次归一化顺带回退了 4 处已跟踪文件的改动
   （`app_id.rs`、`commands.rs`、`root.rs`、`AGENTS.md`），已重做并复验。
   **往后再做仓库级重置前，先 `git stash` 或先把改动落到新文件。**
