# MPelyoffice 对抗式审查报告

版本：0.1（第一轮）
日期：2026-10-20
审查对象：`feat/mpelyoffice-windows` 分支上已落地的代码与配置（fork of ELY-Open-Source/ElyOffice @ `a5af55f`）
审查性质：**红队**。目标是证明这份实现不成立，而不是确认它成立。

---

## 0. 协议

| 项 | 规定 |
| --- | --- |
| 执行者 | 审查者与实现者分离；审查者只以"找出可复现的问题"为目标 |
| 证据要求 | 每条发现必须给出**可复现步骤或代码事实**；不接受"可能有问题""理论上" |
| 攻击面 | ① 安全 ② 数据完整性 ③ 许可与供应链 ④ 性能与资源 ⑤ Windows 集成 ⑥ 可用性与无障碍 |
| 分级 | **P0** = 数据丢失 / 安全漏洞 / 许可违规（必须修复）；**P1** = 功能性错误或需求未达成（必须修复或明确降级声明）；**P2** = 体验瑕疵（记录）；**P3** = 改进建议 |
| 闭环 | 发现 → 定级 → 修复 → **新增回归测试** → 复验 → 留档。禁止"已修复"而无证据 |
| 禁止 | 以"上游也这样"为由豁免；以"尚未实现"为由静默跳过（未实现须明确写进本报告与支持矩阵） |

## 1. 本轮范围与诚实声明

**已落地并可验证**：M0 尖峰 A（GPUI-on-Windows 编译与运行）、M1 统一外壳骨架（功能区 / 混排标签栏 / 开始页 / 状态栏 / 调度器 / 文本引擎 / 命令行打开 / 单实例交接接线）、Windows 集成规范与打包规范文档集（`docs/mp/00`–`07`、`09`）。

**尚未落地**：M2 引擎动态化（`EngineDyn`）、M3 文件关联注册与安装器、M4 六个格式的真实编辑内核（依赖 M0-B 的 LOK 构建）、M5 分发。
**本报告不为其背书**；凡属未落地能力，一律按"需求未达成"记入 P1，并在 `06-格式支持矩阵与许可合规表.md` 中明示。

## 2. 发现清单

### 2.1 P0 —— 数据丢失 / 安全 / 许可

| 编号 | 发现 | 证据 | 状态 |
| --- | --- | --- | --- |
| **P0-01** | **文本文件的 BOM 在保存后丢失**：原实现按 UTF-8 读取（去掉 BOM）后按 UTF-8 写回，字节序标记消失，Excel/记事本等依赖 BOM 判定编码的软件会误解码 | `apps/mpelyoffice/src/text.rs` 的 `decode()`/`store()`；回归测试 `a_byte_order_mark_survives_a_round_trip` | **已修复**（保留 BOM，读写一致） |
| **P0-02** | **非 UTF-8 文件被有损改写**：原实现对任何非 UTF-8 字节用 `from_utf8_lossy` 转成 U+FFFD，保存后**原文字节永久丢失**（GB18030 中文文件变乱码） | 修复前 `read_text()` 即为该行为；回归测试 `chinese_text_outside_utf8_is_kept_as_it_was` | **已修复**（UTF-8 / UTF-8+BOM / UTF-16LE / GB18030 四种往返保真） |
| **P0-03** | **关闭窗口时未保存的修改直接丢失**：原实现没有 `on_window_should_close` 守卫，用户按 X 即丢内容 | 修复前 `apps/mpelyoffice/src/office.rs` 无 `should_close` | **已修复**（有未保存时拦截，并给出「保存并关闭 / 放弃并关闭 / 取消」） |
| **P0-04** | **外部修改的文件被静默覆盖**：原实现保存时不比对磁盘状态，用户在别处改过的文件会被窗口里的旧内容覆盖 | 修复前 `save()` 直接写盘 | **已修复**（保存前比对 `长度 + 修改时间`，不一致则拒绝写入并提示） |
| **P0-05** | **PDF 引擎的许可红线未闭合**：本 fork 仍依赖 `crates/ely-pdf-engine`（链接 **MuPDF，AGPL-3.0**）。若把该 worker 随安装包分发，整个发行包须按 AGPL 履行 | `crates/ely-pdf-engine/Cargo.toml` 链接 `engines/mupdf-build`；上游 `AGENTS.md` 2026-10-19 条 | **已闭合**：PDF 引擎改为 **PDFium（BSD-3）+ 本项目自写 FFI**（`crates/ely-engine/src/pdfium.rs`），**不链接 MuPDF**，也不用 GPL 的 `pdfium-rs`；上游 `ely-pdf-engine` 留在 fork 中但**不进入分发包**（构建期 LC-02 阻断）。实测：PDF 在统一窗口内逐页渲染成功 |

### 2.3 P2 —— 体验与一致性

| 编号 | 发现 | 说明 |
| --- | --- | --- |
| P2-01 | 标签不支持拖出成独立窗口（需求 SH-05） | WPS 的核心交互之一；组件库 `shell::TabBar` 有 `on_reorder`，拖出需自实现 |
| P2-02 | 无自动保存与恢复副本（上游 `ely_office::Recovering` 已有） | 崩溃后未保存内容不可恢复；M2 复用上游实现即可 |
| P2-03 | 状态栏用 `·` 拼接，无标签与图标 | 违反 UX-11（不仅靠颜色/符号表达状态） |
| P2-04 | 超大文件无上限保护，整文件读入内存 | 上游 ely-mark 对 2 MiB 以上只给源码视图；本实现应对超限文件降级并提示 |
| P2-05 | 非 UTF-8 一律按 GB18030 解码，Shift_JIS / Big5 文件会乱码 | 上游有完整探测表（UTF-8/UTF-16/GB18030/Big5/Shift_JIS/EUC-KR/…）；本实现只覆盖 4 种 |
| P2-06 | 保存到符号链接时会替换链接本身而非目标 | `rename` 的语义；需按文件身份（`dunce::canonicalize`）判定后再决定 |
| P2-07 | 外部修改检测只看长度与修改时间 | NTFS 的时间精度为 100ns，实践中足够；跨 FAT32/网络盘（1 秒精度）可能漏检 |
| P2-08 | 未设置 `AppUserModelID` | 任务栏分组与跳转列表无独立身份 |
| P2-09 | 未做 150% / 200% DPI 与多屏验证 | 需求 UX-10 未验证 |
| P2-10 | 图标为本项目自绘（`packaging/icons/mpelyoffice.py`），与上游 Papirus 风格不一致 | 品牌一致性；图标许可为本项目自有 |
| P2-11 | 新建文档的"格式"仅体现在名字里（`text 1`、`markdown 2`），无模板、无默认扩展名 | 与 WPS 的"新建→模板→另存为"流程差距明显 |

## 3. 攻击面逐项结论

| 攻击面 | 结论 |
| --- | --- |
| ① 安全 | **未发现可利用漏洞**，但覆盖面窄：只解析纯文本，不解析任何二进制文档格式；无网络访问；无自动更新。**遗留风险**：恶意超大文件可耗尽内存（P2-04）；写文件无 TOCTOU 缓解（低，因写入路径来自用户选择） |
| ② 数据完整性 | 发现并修复 4 项 P0（BOM、编码、关闭丢数据、外部覆盖）。**仍有 P1-01（标签关闭丢数据）与 P1-08（临时文件名）** |
| ③ 许可与供应链 | **P0-05 已闭合**：PDF 引擎换成 PDFium(BSD-3)，自写 FFI，不链接 MuPDF/AGPL，也不使用 GPL 的 `pdfium-rs`；自有代码 MIT（沿用上游 2026-10-19 的变更）；新增依赖仅 `encoding_rs`（Apache-2.0/MIT）与 `image`（MIT/Apache-2.0）；PDFium 的 Chromium 许可声明随包 |
| ④ 性能与资源 | 冷启动未实测（LOK 未就绪前只测了"窗口开"）；标签数无上限；大文件无保护 |
| ⑤ Windows 集成 | GPUI-on-Windows 已实测通过（Direct3D 11.1、中文排版修正生效、窗口与日志正常）；**关联注册、安装器、单实例实测均未做**（P1-05/06/07） |
| ⑥ 可用性与无障碍 | 硬编码中文（P1-03）；无键盘导航验证；无 AX 树核对（上游的真窗口脚本在 macOS 用 AX，Windows 需另找手段，如 UI Automation） |

## 8. 第二轮（新增代码：PDF 引擎、LOK 引擎、安装器、关联脚本）

### 8.1 发现与处置

| 编号 | 发现 | 证据 | 状态 |
| --- | --- | --- | --- |
| **P0-07** | **关闭窗口：第二次请求会放行**。`should_close` 第一次拦截后把 `pending_close` 置真，第二次直接 `return true` —— 用户连按两次 X 就**绕过询问丢数据** | `office.rs::should_close`（修复前有 `if self.pending_close { return true; }`） | **已修复**：有未保存时**永不**因关闭请求放行，只有询问条里的按钮能结束（保存并关闭 / 放弃并关闭） |
| **P0-08** | **提示从不显示**：`self.notice` 被写了但没有任何界面读它，用户看不到"已保存/已被外部修改/失败" | `office.rs` 中 `notice` 只写不读 | **已修复**：新增 `notice_bar()`，提示显示在功能区下方 |
| **P0-09** | **安装器清单丢掉目录上下文**：`copy_tree` 只记录文件名，嵌套目录里的文件在卸载时找不到 → **卸载不干净**（实测残留 `engines/pdfium/pdfium.dll`） | 实测：清单为 `["pdfium.dll","pdfium","engines"]` | **已修复**：清单改为相对路径（`engines/pdfium/pdfium.dll`），卸载按此删除；实测文件已删 |

## 10. 审查者的自评（两轮合并）

1. 三轮审查只覆盖**本项目新增的代码**（`apps/mpelyoffice`、`apps/mpelyoffice-setup`、`crates/ely-engine`、脚本），未审上游八个 app 的既有实现（不在本次改造范围）。
2. 性能结论薄弱：LOK 未就绪，无法测真实的打开/渲染/输入延迟；上游的 PERF-01..08 基线在 macOS 上取得，**Windows 需重测**。
3. 无障碍结论薄弱：Windows 上未找到与 macOS AX 等价的可自动化手段，需改用 UI Automation 另立方案。
4. 未做模糊测试（fuzzing）：PDFium 绑定与文本解码应补 `cargo-fuzz`（`arbitrary` 字节输入），列入 M2 之后。
5. 第二轮的两条 P1（界面线程阻塞、PDF 首帧一次画 100 页）**有意未修**：它们需要在内核到位、能测量真实卡顿时再定方案，否则是猜测性的重构。
6. 第三轮新增的开始页只有**人工点击与截图**的验证，没有自动化的界面测试（Windows 上尚无可用的 AX 等价物）。
